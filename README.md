# Transaction Ledger API

A RESTful transaction ledger API built with Node.js, Express.js, and PostgreSQL. It supports account creation, credit and debit transactions, balance tracking, transaction history, and atomic account-to-account transfers.

## Features

- Create accounts with UUID identifiers and an initial balance of zero.
- Credit and debit accounts with monetary validation.
- Prevent debits that exceed the available balance.
- Enforce unique reference IDs per account.
- Maintain transaction history with filtering and pagination.
- Perform atomic transfers between accounts.
- Use database transactions and row-level locking to preserve balance consistency.
- Validate requests and return structured error responses.
- Enforce database constraints for data integrity.

## Tech Stack

- Node.js
- Express.js
- PostgreSQL
- `pg` (node-postgres)
- `dotenv`
- `nodemon` for development

## Prerequisites

- Node.js and npm
- PostgreSQL
- Postman or another HTTP client

## Setup

### 1. Clone the repository

```bash
git clone <YOUR_GITHUB_REPOSITORY_URL>
cd transaction-ledger-api
```

### 2. Install dependencies

```bash
npm install
```

### 3. Create the database

Open PostgreSQL and execute:

```sql
CREATE DATABASE transaction_ledger;
```

Create the `accounts` and `transactions` tables, their constraints, and the transaction-history index using the schema documented below.

### 4. Configure environment variables

Create a `.env` file in the project root:

```dotenv
PORT=3000
DB_HOST=localhost
DB_PORT=5432
DB_NAME=transaction_ledger
DB_USER=postgres
DB_PASSWORD=your_local_postgres_password
```

Use your own local PostgreSQL credentials. Never commit `.env` to GitHub.

### 5. Start the server

Development mode:

```bash
npm run dev
```

Production-style local start:

```bash
npm start
```

The API runs at `http://localhost:3000`.

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| GET | `/health` | Check API health |
| POST | `/accounts` | Create an account |
| GET | `/accounts/:accountId/balance` | Get account balance |
| POST | `/accounts/:accountId/transactions` | Create a credit or debit |
| GET | `/accounts/:accountId/transactions` | Get transaction history |
| POST | `/transfers` | Transfer money between accounts |

### 1. Create an account

`POST /accounts`

Request:

```json
{
  "name": "Savings Account"
}
```

Expected status: `201 Created`

The account ID, initial balance, and creation timestamp are generated by the server/database.

### 2. Get account balance

`GET /accounts/:accountId/balance`

Replace `:accountId` with a valid account UUID.

Expected status: `200 OK` for an existing account.

### 3. Create a transaction

`POST /accounts/:accountId/transactions`

Credit example:

```json
{
  "type": "credit",
  "amount": "1000.00",
  "reference_id": "PAYMENT-1001",
  "description": "Initial deposit"
}
```

Debit example:

```json
{
  "type": "debit",
  "amount": "250.00",
  "reference_id": "PAYMENT-1002",
  "description": "Purchase"
}
```

The amount must be a positive decimal string with at most two decimal places. The description is optional.

### 4. Get transaction history

`GET /accounts/:accountId/transactions`

Optional query parameters:

- `type`: `credit` or `debit`
- `page`: page number, starting at 1
- `limit`: records per page, maximum 100

Example:

```http
GET /accounts/<ACCOUNT_UUID>/transactions?type=debit&page=1&limit=10
```

Results are ordered newest first and include pagination metadata.

### 5. Transfer money

`POST /transfers`

Request:

```json
{
  "from_account_id": "<SOURCE_ACCOUNT_UUID>",
  "to_account_id": "<DESTINATION_ACCOUNT_UUID>",
  "amount": "25.00",
  "reference_id": "TRANSFER-1001",
  "description": "Transfer to savings"
}
```

A successful transfer creates a debit transaction for the source and a credit transaction for the destination. Both changes are committed atomically.

## Database Design

### Accounts

| Column | Type | Purpose |
|---|---|---|
| `id` | UUID | Primary key, generated by PostgreSQL |
| `name` | VARCHAR(100) | Required account name |
| `balance` | NUMERIC(18,2) | Stored balance, initially zero |
| `created_at` | TIMESTAMPTZ | Database-generated timestamp |

### Transactions

| Column | Type | Purpose |
|---|---|---|
| `id` | UUID | Primary key |
| `account_id` | UUID | Foreign key referencing accounts |
| `type` | VARCHAR(10) | `credit` or `debit` |
| `amount` | NUMERIC(18,2) | Positive transaction amount |
| `description` | TEXT | Optional description |
| `reference_id` | VARCHAR(100) | Client-provided reference |
| `created_at` | TIMESTAMPTZ | Database-generated timestamp |

A unique constraint on `(account_id, reference_id)` prevents duplicate references for the same account. A foreign key ensures every transaction belongs to an existing account.

## Error Handling

The API uses structured errors:

```json
{
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "Insufficient balance for this transaction."
  }
}
```

Common HTTP statuses:

| Status | Meaning |
|---|---|
| `200` | Successful retrieval |
| `201` | Resource created |
| `400` | Invalid request |
| `404` | Account not found |
| `409` | Duplicate reference ID |
| `422` | Insufficient balance or balance limit exceeded |
| `500` | Unexpected server error |

## Transaction Integrity

- Monetary calculations use PostgreSQL numeric arithmetic.
- Account rows are locked while balances are checked and updated.
- Ledger insertion and balance updates occur within a database transaction.
- Failed operations are rolled back.
- Transfers lock both accounts in a consistent order and commit both sides together.
- Transaction history is read-only through the exposed API; no edit or delete endpoint is provided.
